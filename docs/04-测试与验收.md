# 测试与验收

> 微信开发者工具的命令行在部分机器上受沙箱限制（写 `~/Library/Application Support/微信开发者工具/.cli` 会被拒），所以本项目的验证不依赖 IDE，而是分四层自动完成。

```
npm run check          # 构建数据 → 静态检查 → 单元测试 → 渲染自检
npm run preview:shots  # 启动预览服务，截图 + 交互断言
```

## 1. 第一层：数据构建校验

`scripts/build-data.mjs` 在构建时直接断言，任何一条不满足就 `exit 1`：

| 校验 | 规则 |
| --- | --- |
| 册次字数 | 1a=300、1b=400、2a=450、2b=450、3a=250、3b=250、4a=250、4b=250；去重后 2596（含仅写字表 5 字） |
| 字唯一性 | 跨册重复仅限教材复习字（希/代/章），同一课内不重复 |
| 笔顺完整性 | 每个字必须有 `strokes` 与 `medians`，且条数都等于 `meta.s` |
| 组词 | 每个字至少一个组词，组词拼音音节数必须与字数一致 |
| 坐标范围 | 量化后必须落在 u8 内（否则说明步长选错） |

已知数据缺陷用显式补丁修复（`WORD_PATCH`：`唉`、`哦`），而不是悄悄兜底。

## 2. 第二层：静态检查（`npm run lint`）

不是 ESLint，而是针对小程序特性的 290 行自研检查器：

| 检查项 | 说明 |
| --- | --- |
| 页面四件套 | `pages/X/` 下 `.js/.wxml/.wxss/.json` 必须齐全 |
| app.json 一致性 | `pages` 与磁盘文件双向对应；分包 `root` 目录存在，注册页面存在 |
| tabBar | 2–5 项、页面对已注册、图标存在且 ≤ 40KB |
| WXML | 标签闭合、引号配对、`{{ }}` 配对、`bindtap` 处理函数在 JS 中存在、`{{ }}` 里引用的数据字段在 `data` 里声明 |
| WXSS | 花括号配对、`@import` 目标存在、禁用小程序不支持的 `inset` / `gap` / `aspect-ratio` / `position: sticky` |
| JS | `node --check` 语法、`require` 路径必须解析成功 |
| 分包边界 | 主包不得 `require` 分包文件（反向会包体爆炸） |
| 路由 | 所有 `url: '/xxx'` 必须指向已注册页面 |
| 包体积 | 主包 < 2MB、单分包 < 2MB、总包 < 20MB |

| 断言 | 目的 |
| --- | --- |

### 两个靠测试才发现的真实 bug

**随机数生成器不同步。** `Quiz.mulberry32` 在 Android 上写成
`t *= (1 | t)`，而 JS 原始实现是 `Math.imul(a ^ (a >>> 15), 1 | a)` —
第二个因子是**原来的 a**，不是异或之后的值。同一个 seed 在两端出不同的题。
旧测试只断言了「结果在 0~1 之间」和「可复现」，所以这个 bug 活了 141 个测试。
现在有三组黄金值（seed 12345/42/7）锁死到 1e-15。

**会写字判定错误。** `isWriteChar` 只看 `meta.x` 非空，把 457 个写字课在
五、六年级的字判成本项目要求会写。用户视角的后果是：二年级听写会要求
孩子默写「鸦」「氏」「孙」。修好之后数字从 2255/341 变成 1798/798。

### 第三个靠测试才发现的真实 bug：出题器会卡死

`buildQuiz` 原来用**已出题数**决定取哪个字：

```js
const ch = targets[questions.length % targets.length];
```

某个字出不了题时（比如独体字不出部首题、没有同音伙伴的字不出同音字题），
`questions.length` 不增长，于是**永远重试同一个字**，直到 guard 耗尽——
整套练习变成空白页。

这个 bug 三端都有，而且是潜伏的：多音字和同音字时代，会话层预先把不合格的
字过滤掉了，所以从没暴露。做部首功能时我让独体字不出题，正好踩中——
只要「龟」排在候选第一位，整套题就是 0 道。

修复：改用**尝试次数**推进取字。三端都加了回归测试，
用 `['龟','顶','鼓','披']` 这种「前两个字出不了题」的序列断言能正常出 2 道。

教训是：这类「某个元素不合格就整体卡住」的问题，光靠人工点界面很难发现——
你得刚好抽到那个字排在第一位。测试里构造这种极端序列才抓得住。

## 无障碍：Dynamic Type 怎么验的

iOS 全站 188 处字号都走 `FontSpec` + `@ScaledMetric`，跟随系统字号。这件事
**没法靠看一张截图确认**——默认字号下它和改动前必须逐像素一致（否则就是改坏了），
而放大后是不是"能读"又要人判断。所以分三步验：

### 1. 纯函数可穷举

缩放倍数表 `TypeScale.factor(forStep:)` 和容器缩放 `LayoutRules.scaled` 都是纯函数，
放在 `HanziCore` 测试包里（那个包刻意不依赖 SwiftUI，好在 macOS 上直接跑）。
12 个档位可以逐个断言单调递增、两端夹紧、封顶生效——比截图看一个档位可靠得多。

分栏阈值同理：`detailIsSplit(width, scale:)` 直接断言「787pt 在默认字号下分栏、
最大字号下不分栏」。

### 2. 默认字号必须零变化

改动前后在默认字号下截同一页做像素对比：差异 3826 像素，全部落在
`(51,19)-(460,44)` —— 状态栏时钟。内容区完全一致，说明
`@ScaledMetric` 在 1.0 档精确等于基准值，没有引入浮点漂移。

这条是最容易被忽略的验收点：加缩放机制时很容易顺手把字号"微调一点"，
那就从"修 bug"变成了"改设计"。

### 3. 逐档扫版找溢出

`.tools/tmp/dtsweep.mjs` 用 `xcrun simctl ui <dev> content_size <档位>` 切换档位，
逐页截图，量**内容右缘到屏幕边的距离**。判据不是"有没有内容"，而是
「这个距离会不会随字号变化」——布局正确时它是常数（iPad 上恒为 84px），
字号变化不会把它推向屏幕边缘。

覆盖 12 个页面 × 3 个档位（最小 / 默认 / 辅助功能最大），结果全部稳定。

### 过程中真正修掉的问题

| 问题 | 现象 | 修法 |
| --- | --- | --- |
| 网格最小宽写死 | 字号放大后卡片还是那么窄，文字挤成两行三行 | 最小宽乘以 `dt.layoutScale` |
| 答题选项双列 | 辅助字号下每个选项只剩半宽，汉字被压到看不出结构 | 辅助字号下一律单列 |
| 分栏阈值写死 | 787pt 内容区在最大字号下仍分栏，侧栏每行三四个字 | 阈值也乘缩放，封顶 1.8 倍 |
| 徽章描述固定 24pt 高 | 两行字被裁掉下半截 | `frame(minHeight:)` |
| 汉字图标不跟字号 | 汉字是笔画画的，不随字号走，放大后显得又小又空 | 图标尺寸也乘 `layoutScale` |
| 内容大字封顶 1.6 | 我自己写的原则是"限制正文放大就是拒绝需要它的人"，却一刀切封了 1.6 | 装饰封 1.4、内容封 2.2 与容器同步、正文不封 |

最后一条值得记下来：初版把 16 处 28pt 以上的字号统一封顶 1.6，
理由是"怕撑破卡片"。但这里面有 emoji（该封），也有练习页题干、
描红页汉字提示（**不该封**——用大字号的用户就是要看清它）。
按内容而不是按字号大小来分档，才符合原本的设计意图。

### 多孩子档案最容易踩的坑

**清空学习记录不能误伤兄弟档案。** 第一版 Android 的 `Store.clearAll()`
做法是「先全清，再把 `profiles` 写回去」，结果清空默认档案时把
`p2:progress` 也删了。测试 `清空学习记录只清当前档案` 抓到的：

```
expected:<1> but was:<0>
```

正确做法是按命名空间删：默认档案只删不带 `:` 的 key，其他档案只删
自己的前缀。iOS 的 `clearAll` 在 ns 为空时必须跳过子目录。

**默认档案 id 必须是空串**，不是 `'default'`。因为老用户的存储 key 形如
`hanzi:v1:progress`，加一层命名空间后如果默认档案叫 `'default'`，
key 会变成 `hanzi:v1:default:progress` —— 所有人升级后学习记录归零。
空串让 `keyOf` 退化成原样拼接，key 逐字节不变。

### 识字量测试被测试改掉的四处逻辑

初版 `estimate()` 有四个 bug，全是测试抓出来的：

| bug | 现象 | 修法 |
| --- | --- | --- |
| `break` 提前退出 | 提前停下的那册之后的分组从 `groups[]` 里整个消失 | 去掉 `break`，只置停止标记 |
| `answered` 用 `list.length` | 停止场景报成 40 题 | 改成各组 `asked` 求和 |
| 停止后仍计数 | `asked` 把停止后的作答也算进去 | 改成 `stopped ? 0 : …` |
| 估算超过字库 | 报 2600，字库只有 2596 | 钳到 `catalog.getAllChars().length` |

还有一个是**测试自己写错了**：`verdict` 的断言假设 0 和 50 分属不同档，
但设计上两者都是「刚开始」。改成断言 <100 时相等、>100 时单调递增。

### 字帖导出 PDF：为什么自己拼字节

iOS 用 `UIGraphicsPDFRenderer`、Android 用 `android.graphics.pdf.PdfDocument`
都能直接生成 PDF。但 Android 那条路在 Robolectric 里跑不通
（`PdfDocument` 没有 shadow，`writeTo` 直接抛 `document is closed!`），
而这个环境**没法跑真机**——用它就意味着导出功能永远无法自动验证。

所以三端都自己拼 PDF 字节（PDF 就是「对象 + 交叉引用表」的文本格式）。
好处：字节完全可断言、三端输出一致、不依赖图形栈。

**不嵌中文字体。** 嵌一个中文 TTF 要 3-10MB 还得做子集化。这里一个中文
都不画成文字：汉字全用笔顺轮廓画成矢量路径（界面上描红的范字本来也是
这么画的），只有日期和页码用 PDF 内置的 Helvetica（Base-14，阅读器自带）。
3 页 14 个字 = 131KB，而且放大到 A3 不糊。

测试锁死的东西：

| 断言 | 为什么 |
| --- | --- |
| 每个 `n` 条目的偏移落在 `N 0 obj` 上 | xref 错一位整份文件打不开，是手写 PDF 最易错处 |
| 无 `FontFile` 对象 | 防止不小心把字体嵌进去 |
| 无科学计数法 | `1e-7` 会让阅读器整页空白 |
| 二次贝塞尔升阶控制点在 1/3、2/3 | PDF 没有 `q` 指令，`c1 = P0 + 2/3(Q-P0)` 是**精确**等价 |
| 描红字亮度比格线低 ≥0.05 | 第一版 `#CFC7B6` 与格线 `#C9BDA6` 只差 5 个色阶，打印出来孩子分不清哪条该描 |
| 格子左右边距相等、互不重叠、不出页 | 版式算错要到打印时才发现，纸已经废了 |

发现的三个真实 bug：

1. **`moveTo` / `lineTo` 没维护 `current`。** 只有 `glyphPath` 内部
   手动调 `_setCurrent`，直接调用 `quadTo` 的人会踩空指针。
   测试「二次贝塞尔升阶」直接构造 `moveTo → quadTo` 就崩了。
2. **描红字和格线同色。** 见上表最后一条。
3. **冷启动导出会是白纸。** 见下一节。

### 冷启动导出白纸：分包与主包的冲突

小程序的笔画数据在分包里（每册 0.2~0.45MB），而**主包不能 require 分包**。
现有机制是分包页面启动时把自己的加载器注册进 `strokeStore`：

```js
strokeStore.register('1a', () => require('../../data/strokes-1a.js'));
```

但 `loaders` 只在内存里。用户冷启动 App 直接进「我的字帖」点导出时，
一个分包页面都没执行过，`get()` 全返回 `null` —— 导出的 PDF 是白纸，
而且**没有任何报错**，用户只会觉得"导不出来"。

字帖里的每个字用户都写过，写的那一刻分包一定是加载着的。所以在写成功的
时候顺手把原始 base64 存进本地缓存（`write-page.js` 的 `finish()`），
之后任何时候都能出 PDF。缓存键 `hanzi:v1:outline-cache` **不带档案命名
空间**：同一个字对哥哥和弟弟是同一份数据，按档案各存一份纯属浪费，
而小程序存储上限只有 10MB。上限 600 字（约 0.5MB），超出丢最早的。

顺带挖出另一个 bug：`loadBook` 在没有加载器时会把**空对象**缓存下来，
于是分包页面稍后注册了加载器，这个字仍然永远取不到——正好是冷启动场景。
现在没有加载器时直接返回 `{}`，不写进 `bookData`。

这三条都是先写了用例才发现的，其中第 3 条不看代码根本想不到。

### 三端字形一致性怎么验的

小程序的 `pdf.js` 和 iOS 的 CoreGraphics 是两套完全独立的实现。把两边
导出的 PDF 都渲染成 PNG，逐像素比对：

```
描红字 178,171,151  ← 两端完全相同
范字   38,51,46 / 37,51,45  ← 差 1 个色阶（取整方式不同）
```

差值 1 说明两条渲染路径落到了同一个字形和同一个位置。

## iOS 独有的 bug：换字后画布不刷新

**现象**：描红页右上角「上一个 / 下一个」，点了之后标题、拼音、笔画数都变了，
但画布上的字没换。

**根因**：SwiftUI 在同一个导航层位置上复用视图身份。`pushReplacing` 把栈顶
route 换成另一个字时，`WritePageView` 这个视图并没有被销毁——`@State` 里的
`WriteSession` 活了下来，`.onAppear` 也不再触发。于是 `ch` 变了（标题跟着变），
`session` 没变（画布还是旧字）。

更细的一层：换字那一帧里，`ch` 已是新字而 `session` 还是旧字（`.onChange`
在 body 求值之后才跑）。哪怕加了 `onChange` 重建，那一帧仍会把旧 session
交给 `WritePageBody`，出现「标题新字 + 画布旧字」的自相矛盾画面。

**修法（两层）**：

1. `navigationDestination` 加 `.id(r.ch)`：换字 = 换视图身份，`@State` 彻底重来
2. 视图内部用 `liveSession`：`session.ch != ch` 时**不渲染**，宁可闪一帧加载态

**为什么另外两端没有这个问题**：Android 用 `remember(ch)`，状态键就是字本身；
小程序在同一个页面实例里显式重置了 `strokeIndex / done / liveScore` 等全部状态。
只有 iOS 把「会话对象」放进了 `@State`，而 `@State` 不跟随导航参数变化。

**怎么验证的**：加 `-writeStep N` 调试参数，走导航栏按钮**完全同一条**代码路径
（`pushReplacing`），然后比对截图。

```
修复前：点「下一个字」后，画布区域像素差 = 0
修复后：天 +1 → 与直接打开「地」像素差 = 0
       天 +3 → 与直接打开「你」像素差 = 0
       你 -3 → 与直接打开「天」像素差 = 0
```

（「修复前的 0」和「修复后的 0」含义相反：前者是「画布没动」，后者是
「和直接打开完全一致」。）

**顺带修掉的探针缺陷**：探针挂在 `onAppear` 里，而 `.id(ch)` 让每换一个字
都重跑 `onAppear`，结果每换一次就再排一轮自动翻字，3 步会一路跑到本课最后
一个字。加了一次性闩。这个缺陷本身挺说明问题：如果只看"最后停在某个字"就下
结论，会误判成"修复无效"。

## 描红页的「上一个 / 下一个」：三端补齐 + iOS 换字不刷新

### 起因

iOS 描红页右上角有「上一个 / 下一个」，点击后**字没换**。修的过程中发现
另外两端**根本没有这个按钮**——所以这不只是修 bug，是补齐一个只在 iOS 上
存在的功能。

### 三端的实现与位置

| | 位置 | 实现 |
| --- | --- | --- |
| iOS | 导航栏右上 | `.toolbar` + `pushReplacing` |
| Android | 画布下方按钮行 | `PagerButton` + `nav.replace` |
| 小程序 | 页面底部 `.pager` | `onPager` + `loadChar` 原地换字 |

**iOS 为什么放导航栏而不是页脚**：页脚已经挤了「重写 / 跳过一笔 / 写完」
三个按钮，再加两个会溢出（`footerStacks` 就是为这个加的）。这是有意的位置
差异，不是不一致。Android 和小程序的空间够，放页脚更顺手。

三端都只在**描红**模式显示，听写模式不显示——听写是「按课文顺序默写」，
翻字会打乱它的推进逻辑（听写页有自己的推进回调 `onFinished`）。

三端都采用 **replace 语义**（不加深返回栈）：连翻十个字不该需要按十次返回。

### iOS 换字不刷新的根因

SwiftUI 在同一个导航层位置上复用视图身份。`pushReplacing` 把栈顶 route 换成
另一个字时，`WritePageView` 并没有被销毁——`@State` 里的 `WriteSession` 活了
下来，`.onAppear` 也不再触发。于是 `ch` 变了（标题、拼音、笔画数跟着变），
`session` 没变（画布还是旧字）。

body 求值之后才跑）。哪怕加了 `onChange` 重建，那一帧仍会把旧 session 交给
画布，出现「标题新字 + 画布旧字」的矛盾画面。

1. `navigationDestination` 加 `.id(r.ch)`：换字 = 换视图身份，`@State` 彻底重来

**为什么另外两端没有这个 bug**：Android 用 `remember(ch)`，状态键就是字本身；
小程序在 `loadChar` 里显式重置了全部状态。只有 iOS 把会话对象放进了 `@State`。

### 怎么验证的

iOS 加了 `-writeStep N` 调试参数，走导航栏按钮**完全同一条**代码路径
（`pushReplacing`），然后比对截图：

```

修复后：天 +1 → 与直接打开「地」像素差 = 0
       天 +3 → 与直接打开「你」像素差 = 0
       你 -3 → 与直接打开「天」像素差 = 0
```

小程序用预览环境直接点按钮，读 DOM 验证：

```
初始     天 / tiān / 上一个禁用
点下一个  地 / dì
再点      人 / rén
点上一个  地 / dì
```

Android 用 Compose 测试点按钮，断言 `nav.current` 变成了预期的字。

### 探针本身的一个坑

iOS 的探针挂在 `onAppear` 里，而 `.id(ch)` 让每换一个字都重跑 `onAppear`，
结果每换一次就再排一轮自动翻字，3 步会一路跑到本课最后一个字。加了一次性闩

| 上一个能回到前一个字 | 预览 + DOM | ✓ | ✓ |

## 底部导航只在三个根页面出现（iOS 漏了）

**要求**：底部导航（首页 / 练习 / 我的）只在三个 tab 根页面显示，进入详情
就隐藏。

**iOS 的问题**：`TabView` 推入页面后，底部标签栏默认还贴在下面，占着约 49pt。
而详情页自己的页脚本来就有「描红 / 听写 / 练这个字」这排操作，两排叠在
一起既挤，又分不清哪个是"换页"、哪个是"做事情"。

**另外两端本来就是对的**：

- Android：`TAB_ROOTS = {Index, Practice, Profile}`，`if (isTabRoot(screen)) BottomBar(...)`
- 小程序：`app.json` 的 `tabBar.list` 只有三个页面，其余页面天生没有 tabBar

所以这又是一处 iOS 独有的偏差。

**修法**：在 `AppRoutes` 的每个 `navigationDestination` 上挂 `.pushedScreen()`
（内部就是 `toolbar(.hidden, for: .tabBar)`）。11 个 destination 全覆盖。
iPad 走 `NavigationSplitView`，本来没有 tab 栏，这里是空操作。

### 为什么逐个挂而不是在 NavigationStack 上统一设

试过的方案是在 `PhoneRootView` 的 `NavigationStack` 上按 `path.isEmpty` 动态
设置 `.toolbar(path.isEmpty ? .visible : .hidden, for: .tabBar)`。没采用，因为
那个值要随导航栈变化重算，而 `tab(_:_:_:)` 里拿不到每个 tab 自己的 path
（`app.pathBinding(section)` 是 computed，不是可观察状态），会读到旧值。
逐个 destination 挂虽然啰嗦，但每个页面自己声明，行为确定。

### 验证

用 `-startRoute` 逐个进页面，量底部 242px 条的主色：

| 页面 | 推入后底部 | 结论 |
| --- | --- | --- |
| 详情（char:天） | 全白 182525 | tab 栏已隐藏 |
| 课本 / 课时 / 字帖 / 错题 / 关于 / 识字量 | 纸色铺满 | tab 栏已隐藏 |
| 首页 / 练习 / 我的 | 有 tab 栏内容 | 正常保留 |

**返回后 tab 栏能不能回来**：这一条必须实测——iOS 曾经有「弹栈后 tab 栏再
也不出现」的 bug。加 `-popAfter N` 参数，推入后 N 秒弹回根页面：

```
推入详情时底部：255,255,255 182525  ← 全白，无 tab 栏
返回根页后底部：255,252,244 20866   ← tab 栏回来了
```

### 新增的跨端断言

这类「三端行为应该一致、但实现方式完全不同」的地方最容易漏，所以直接读
三端源码比对（`tests/cross-platform.test.mjs`）：

| 断言 | 防的是什么 |
| --- | --- |
| iOS 每个 destination 都调了 `pushedScreen()` | 漏挂一个，那个页面底部就多一条 |
| `pushedScreen` 内部真的调 `toolbar(.hidden, for: .tabBar)` | 修饰符被改成空实现 |
| Android `BottomBar` 以 `isTabRoot(screen)` 为条件 | 条件被改成恒真 |
| 小程序 `tabBar.list` 只有三个根页面 | 有人往里面加页面 |
| 三端的 tab 根集合一致 | Index/Practice/Profile ↔ home/practice/profile |

写完后特意验过第一条会变红：去掉一个 `pushedScreen()` 后报
「11 个 destination 里只有 10 个调了 pushedScreen()」。

## 四个新功能：周报 / 选字做字帖 / 部首归类 / 词语表

这一批的共同点是**没有新增任何数据**——四份数据都早就在仓库里躺着，
只是从来没有被展示出来过。所以这批的难点不在算，在口径。

| 功能 | 数据本来在哪 | 此前被谁用过 |
| --- | --- | --- |
| 学习周报 | `stats.days` 逐日 `{learned, answers, correct}` | 只有「活跃天数」一个徽章间接读过 |
| 选字做字帖 | 课时生字 / 错题 / 星级 / 薄弱笔画 | 各自单独的页面，没有合并成"要练的字" |
| 部首归类 | `meta[ch].r`（237 个部首） | 只有「这个字的部首是什么」这道题 |
| 词语表 | 121 个课时的 1266 条词语 | 只在「看拼音选词语」的题目里 |

### 学习周报

**为什么是滚动 7 天，不是周一到周日**：日历周有个很难受的副作用——周一
早上打开，整周几乎全是空的，看起来像"什么都没做"。滚动 7 天任何时候打开
都有内容。代价是同一个字可能被算进两周，但周报是看趋势的，不是做账。

**三个口径必须钉死**，算错了比不显示更糟（家长会据此判断孩子学得好不好）：

1. **缺数据的那天算「没学」，不能算 0 分**。`stats.days` 里没有那天的键，
   如果按 `{learned:0, answers:0, correct:0}` 填，正确率会显示 **0%**——
   家长看到的是"孩子全答错了"，而事实是"那天根本没打开"。
2. **只描红没答题时，正确率是 `null` 不是 0%**。有学习量但没答题，
   算不出正确率，界面显示「—」和「没答题」。
3. **没有「最好的一天」就是 `null`**，不能拿一个全 0 的天充当。

**柱状图的归一化**：按 `max(learned, ceil(answers/4))` 归一，不是只看
`learned`。否则"今天复习了 30 道题"会画成一根空柱子——那天明明学了很多。
另外活跃的那天给一个最小比例 0.08，不然 1 个字相对 100 个字，柱子只有
零点几像素，看起来像没学。

**建议措辞**：只描述做了什么，不评价孩子。「这周学了 23 个字」比
「学习不够努力」有用。空周只给一句话，不刷屏。

### 选字做字帖

「我的字帖」只能导**写过的字**，但家长真实的用法是「把这课的生字打一张」
「把错题打一张」——这些不是"我写过的"，是"我需要练的"。

四条来源合并去重，优先级 **错题 > 笔画弱 > 课时 > 低分**：一个字可能
同时是错题和本课生字，标签合并显示成「错题 · 课时」，排在最前面的是最该练的。

**小程序端有一个绕不过去的限制**：笔画数据在分包里，主包取不到，
`strokeStore` 只认得本次会话加载过或之前缓存过的字。所以选中一个没描过的字，
画出来会是**空田字格**。

处理方式是**在选字时就标出来**，而不是导出一张缺字的纸让孩子描格子：

- 能导的正常显示
- 不能导的置灰，写「点我去描」，点一下直接跳到那个字的描红页
- 页面顶部说明有几个字画不出来、原因是什么、怎么办

这是三端唯一不一致的地方：Android 和 iOS 的笔画数据是打进包的，没有这个
限制，所以不做置灰。

### 部首归类

237 个部首分布极不均：口 144 字、扌 138、氵 132，但有 **54 个部首只带 1 个字**。
所以默认按字数从多到少排，冷门部首排在后面，不至于一进来就被一堆单字部首淹没。

归类的价值在横向对比：认识「氵」之后，看到江、河、湖、海都带三点水，
才明白"部首"是什么意思。这个页面就是给这个"啊哈"时刻准备的。

`inLib` 标志部首字本身在不在字库里（「口」在，能点进详情；「氵」是偏旁形态，
字库里没有这个字，不能点）。

### 词语表

课文词语表里 121 个课时共 **1276 条课本词**。但这里有个容易踩的坑：

**一年级课本没有词语表**（教材本身就没有）。所以 `utils/words.js` 早就做了
兜底——用每课生字的第一组词补上，标成 `from: 'derived'`。这个兜底在我第一版
实现里被漏掉了，因为我在 `catalog.js` 里另写了一套遍历。结果是**一年级点进
词语表看到一片空白**，而一年级正是这个 App 最大的用户群。

所以这一页直接用 `words.bookWords()`，不另写一套。

**册次是混的，不是"一年级全派生、其他全课本"**：

| 册 | 总词数 | 其中派生词 |
| --- | --- | --- |
| 1a / 1b | 264 / 366 | 全部 |
| 2a / 2b | 320 / 363 | 92 / 91 |
| 3a / 3b | 304 / 298 | 102 / 100 |
| 4a / 4b | 294 / 283 | 103 / 111 |

2a 有的课文有词语表、有的没有，所以不能用 `every` 判一下就下"这册没有词语表"
的结论，要报数量并分两种措辞（全册派生 / 部分派生）。

**两种去重粒度**，这是另一个容易错的地方：

- **分组浏览按册去重**：2492 条。「旅行」在 1b 和 3a 各出一次是教材事实，
  分组时该各显示一次。
- **搜索和总数全局去重**：**1967 个词**。否则搜「行」会列出两条「旅行」。

**还有 19 个派生词含字库外的字**（「弓弩」的弩、「镜匣」的匣——取自组词，
而组词可能用到 2596 字之外的常用字）。那些字点不进详情页，要置灰，
不然用户点了以为卡住。

**「学会」的定义**：一个词里**每个字都学过**才算。有一个字不认识，这个词
孩子读不出来，算学过是自欺欺人。

统计：1967 个词（按册 2492 条）、237 个部首、8 册都有词语、12429 组形近字。


### 三端移植与黄金值

Android 和 iOS 是照着小程序抄的。抄的过程本身抓出了一个参考实现的 bug：

**选字顺序和标签顺序反了**。`copybook-pick.js` 的 `build()` 里 push 顺序是
「错题→弱笔→低分→课时」，而 `FROM_ORDER`（标签顺序）是「错题→弱笔→课时→低分」。
两处不一致的结果是：标着「课时 · 低分」的字可能排在纯课时字前面，用户没法
解释这个顺序。子代理照抄时发现注释和代码自相矛盾，指出来才修掉——
说明"照着另一端抄"这个做法本身也是一种审查。

**三端黄金值**。周报的数字给家长看，算错了比不显示更糟。所以拿同一份输入
（六天有数据、前天故意留空）在三个实现里各跑一遍，逐字比对：

| | 三端输出（完全一致） |
| --- | --- |
| headline | `这周来了 6 天，很稳` |
| 汇总 | learned 24 / answers 54 / correct 47 / accuracy 87 / activeDays 6 / empty false |
| 逐日学习量 | `4,2,3,6,0,4,5` |
| 柱高 | `0.67,0.33,0.5,1,0,0.67,0.83` |
| 结论 | `这周认识 24 个字，答题 54 道，来了 6 天` |
| 建议 | `good:这周认识了 24 个字，平均每天 4 个。` / `good:答题正确率 87%，很扎实。` / `plain:有 1 天没有学习记录。每天固定一个时间学，比一次学很久有用。` |

这组值钉在 `tests/report.test.mjs` 里，改任何一端口径都会红。

### 移植时的两处偏差（有意为之）

1. **iOS 的 `bookWords` 加了缓存**。不加的话词语页每次 body 求值都要重算
   八册词（每个词都要过一遍 `meta` 查拼音），页面推入后空白好几秒。
2. **iOS 的选字页加了换课菜单**。小程序的 `onPickLesson` 在 markup 里没有
   对应的 UI——写了个处理器却没给入口，"本课生字"实际不可达。

### 一个取证工具的缺陷

`TapTargetProbe`（实测控件尺寸的那个）原本用 `flushed` 闩只写一次，由启动后
固定 1.2 秒触发。页面稍慢一点没布局完，就只记到首页控件——**而文件照样生成**，
看起来像"这个页面没有需要量的控件"。

我拿词语表页实测过：等 4 秒只探到「首页-今日一字」，等 6 秒三个控件全在了。
这种"静默漏数据"的取证工具比没有更危险。

改成可以重复 flush，由调用方在 0.8/1.6/2.5/4/6 秒各调一次，每次覆盖写。
修完立刻暴露出两个此前没被发现的问题：**周报页一个探针都没有**（它没有任何
交互控件，属正常）、**选字页的字格（主要交互）没挂探针**（这才是真漏）。
后者补上后实测 83x78，达标。

### 截图取证在这次失效了

iOS 模拟器截图从某个时刻起带一层 `204,204,204` 的灰色遮罩，平均亮度从
正常的 0.96 掉到 0.78。这不是 App 的问题——换成系统 App 截一样有。
所以这一轮 iOS 的视觉验证只能靠 `-probeTapTargets`（代码报数，不走截图），
配合 ASCII 结构检查。像素级比对这次做不了，如实记下来。
